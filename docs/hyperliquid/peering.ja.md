# ピアリングアクセス

ピアリングは、非バリデーティングノードに対して、mempool を含む低レイテンシで重複排除された Hyperliquid ゴシップフィードを Block Proxy 経由で提供します。Edge マーケットデータフィードは含まれません。Edge については [Subscribe to Hyperliquid (Edge)](edge.md) をご覧ください。概要: [Hyperliquid](index.md)。

| | |
|--|--|
| 対象者 | お客様が運用する非バリデーティングノード |
| 提供内容 | Block Proxy 経由の調停済みゴシップフィード 1 本（ブロック + mempool） |
| 受信ホスト | IP 1 つを含む |

| 可用性目標 | 月間 99.9% |

## ピアリングのリクエスト

ピアリングに関する詳細情報は [Telegram](https://t.me/doublezero_telegram_bot?start=fromwebsite) からご確認いただけます。ノードの静的パブリック IP（およびリージョン）を含めてください。ノードの詳細情報と決済が完了してから **1〜3 営業日** 以内にピアの詳細をお知らせします。

## 有料ピアリングの理由

パブリックな Hyperliquid ルートピアは共有されています。スロットは競合し、ピアはローテーションやレートリミットが行われ、多くは mempool を転送しません。予約済みピアリングスロットにより、パブリック容量を奪い合うのではなく、DoubleZero 上の安定したアップストリームが得られます。

## 仕組み

- 2 つのゴシップソース: Hyper Foundation の非バリデーティングノードからの A フィードと、セントリーからの B フィード。
- お客様は水平にスケールする Block Proxy ティアとピアリングします。各プロキシは当社の両方の非バリデーティングノードとピアリングし、それぞれに対して 1 つの通常のゴシップピアとして見えます。
- プロキシは A と B を調停して、ピア向けに 1 つの重複排除されたゴシップフィードにまとめるため、いずれかのソースが落ちてもストリームは停止しません。
- プロキシを追加して容量を拡大できます。当社の非バリデーティングノードへの負荷はピア数に応じて増加しません。

Hyper Foundation ノードが当社のプライマリとピアリングし、セントリーがセカンダリにフィードを供給します。各 Block Proxy は両方とピアリングし、お客様向けにフィードを統合して、必要に応じてスナップショットサービスからブートストラップスナップショットを取得します。

## アップタイム

目標: 月間 99.9% の可用性。

- 冗長フィード。各プロキシは当社の両方の非バリデーティングノードとピアリングします。これらのノードは独立したソース（Foundation とセントリー）からブロックを取得します。セッションまたはソースの一方が落ちた場合、障害パスが復旧する間、もう一方がブロックの供給を継続します。
- 当社のノードはプロキシティアの背後に位置します。外部ピアは Block Proxy にのみ到達します。プロキシが障害を起こした場合、そのピアは別の正常なプロキシに再接続します。負荷が当社のノードにフォールバックすることはありません。
- プロキシは使い捨てのキャッシュ（スナップショット、ローリングブロックウィンドウ、ライブバッファ）のみを保持し、権威あるチェーンステートは持ちません。障害のあるプロキシは自動的に置き換えられます。代替プロキシは、アップストリームセッションとキャッシュがレディネスチェックに合格した後にのみサービスに投入されます。その際、当社の非バリデーティングノードは再起動されません。

## オートスケーリング

- プロキシを追加してスケールします。各プロキシは多数のピアを処理しますが、当社の各非バリデーティングノード上では単一のピアとしてカウントされます。
- ノードの負荷はピア数ではなく、プロキシ数に追従します。
- 新しいプロキシはキャッシュがウォームアップされ、レディネスチェックに合格した時点で起動します。フルチェーンの再同期は必要ありません。
- 参加するピアはスナップショットサービスからブートストラップスナップショットを、プロキシ自身のストアからキャッチアップブロックを取得します。当社の非バリデーティングノードからは取得しません。新規ピアの急増はプロキシティアが受け止めます。
