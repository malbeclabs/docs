# ピアリングアクセス

ピアリングは、非バリデーティングノードに対して、メモリプールを含む低レイテンシで重複排除された Hyperliquid ゴシップフィードを Block Proxy 経由で提供します。Edge マーケットデータフィードは含まれません。それらについては [Subscribe to Hyperliquid (Edge)](edge.md) をご覧ください。概要：[Hyperliquid](index.md)。

|--|--|
| 対象者 | お客様が運用する非バリデーティングノード |
| 提供内容 | Block Proxy 経由の調停済みゴシップフィード 1 本（ブロック＋メモリプール） |
| 受信ホスト | IP 1 つを含む |
| 料金 | $999/月（Edge マーケットデータなし） |
| 可用性目標 | 月間 99.9% |

## ピアリングのリクエスト

ピアリングに関する詳細情報は [Telegram](https://t.me/doublezero_telegram_bot?start=fromwebsite) で入手できます。ノードの静的パブリック IP（およびリージョン）をお知らせください。ノードの詳細情報とお支払いが完了してから **1〜3 営業日** 以内にピアの詳細をお送りします。

## ノードの接続

承認後、**ピア IP** をお送りします。非バリデーティングノードをそのピア IP に向け、ファイアウォールを開放し、ノードを再起動してください。

### 1. ゴシップ設定の構成

`~/override_gossip_config.json` を以下の内容に置き換えてください。ピア IP を使用します：

```json
{
  "root_node_ips": [{"Ip": "<PEER_IP>"}],
  "try_new_peers": false,
  "split_client_blocks": true,
  "chain": "Mainnet"
}
```

| 設定 | 理由 |
|--|--|
| `root_node_ips` | DoubleZero ピアが唯一のアップストリームです。 |
| `try_new_peers: false` | ノードを DoubleZero ピアに固定します。パブリックピアには切り替わりません。 |
| `split_client_blocks: true` | メモリプールトランザクションを `~/hl/data/mempool_txs/` にストリーミングします。 |

### 2. ピアに対してファイアウォールを開放

**`<PEER_IP>` からのインバウンド TCP および UDP 4001–4002** を許可してください。クラウドセキュリティグループとホストファイアウォールの両方で設定します。

ノードが接続すると、ピアはノードの 4001 および 4002 ポートに接続し返して到達可能かどうかを確認します。このチェックがブロックされると、接続は確立されますがデータは到着しません。ピアへの 4001–4002 のアウトバウンド接続も許可してください。

### 3. ノードの再起動

```bash
sudo systemctl restart hl-node   # or however you run hl-visor
```

ノードは起動時にこのファイルを読み込みます。実行中に行った変更は完全に反映されない場合があるため、変更のたびに再起動してください。キャッチアップには通常 5〜15 分かかります。

### 4. 動作確認

```bash
ss -tn state established '( dport = :4001 )'     # one connection, to <PEER_IP>
journalctl -u hl-node -f | grep 'applied block'  # blocks are being applied
ls -l ~/hl/data/mempool_txs/                     # mempool files are growing
```

!!! warning "接続済みだがデータなし"
    ピアがノードの 4001–4002 に到達できません。ステップ 2 のインバウンドルールを確認してください。

!!! note "パブリックピアへのフォールバックなし"
    `try_new_peers: false` の場合、ノードは DoubleZero ピアに到達できないと待機し続けます。パブリックピアには切り替わりません。`Peer full` やコネクションタイムアウトが繰り返し表示される場合は、お問い合わせください。

## 有料ピアリングの理由

パブリック Hyperliquid ルートピアは共有されています：スロットは競合し、ピアはローテーションやレート制限を受け、多くはメモリプールを転送しません。予約済みピアリングスロットは、パブリック容量を奪い合う代わりに、DoubleZero 上の安定したアップストリームを提供します。

## 仕組み

- 2 つのゴシップソース：Hyper Foundation の非バリデーティングノードからの A フィードと、セントリーからの B フィード。
- お客様は水平にスケールする Block Proxy ティアとピアリングします。各プロキシは両方の非バリデーティングノードとピアリングし、それぞれのノードからは通常のゴシップピア 1 つとして見えます。
- プロキシは A と B を調停し、ピア向けに 1 つの重複排除済みゴシップフィードにまとめます。どちらかのソースがダウンしてもストリームは停止しません。
- プロキシを追加すれば容量が増えます。非バリデーティングノードへの負荷はピア数に応じて増加しません。

## アップタイム

目標：月間可用性 99.9%。

- 冗長フィード。各プロキシは両方の非バリデーティングノードとピアリングしています。これらのノードは独立したソース（Foundation とセントリー）からブロックを受信します。一方のセッションまたはソースがダウンしても、障害パスが復旧する間、もう一方がブロックの流れを維持します。
- 当社のノードはプロキシティアの背後にあります。外部ピアは Block Proxy にのみ到達します。プロキシが障害を起こした場合、そのピアは別の正常なプロキシに再接続します。負荷が当社のノードにフォールバックすることはありません。
- プロキシは使い捨てのキャッシュのみを保持します（スナップショット、ローリングブロックウィンドウ、ライブバッファ）。権威あるチェーンステートは保持しません。障害プロキシは自動的に置き換えられます。代替プロキシは、アップストリームセッションとキャッシュのレディネスチェックに合格してからサービスに投入されます。そのために当社の非バリデーティングノードが再起動されることはありません。

## オートスケーリング

- プロキシを追加することでスケールします。各プロキシは多数のピアにサービスを提供しますが、各非バリデーティングノードでは単一のピアとしてカウントされます。
- ノード負荷はプロキシ数に連動し、ピア数には連動しません。
- 新しいプロキシはキャッシュがウォームアップされレディネスチェックに合格すると起動します。フルチェーン再同期は不要です。
- 参加するピアはスナップショットサービスからブートストラップスナップショットを取得し、キャッチアップブロックはプロキシ自身のストアから取得します。当社の非バリデーティングノードからは取得しません。新規ピアの急増はプロキシティアが受け止めます。
